     - Verification and Self-Review:
       - Types: Checked for consistency between interfaces and implementations. CmsComment includes tenant, entryId, 
   modelId which are crucial for multi-tenancy and data isolation.
       - Storage: Used a PK pattern T#<tenant>#CMS#MODEL#<modelId>#ENTRY#<entryId>#COMMENTS which allows efficient 
   querying of all comments for a specific entry.
       - GraphQL: Exposed standard CRUD operations. getComment, updateComment, deleteComment require entryId and modelId 
   to correctly locate the record in DynamoDB (due to the PK design).
       - Threading: parentId field in CmsComment allows building threaded UI on the frontend.
       - Tagging: Supported implicitly via body text.
       - Security: createCommentsCrud checks for tenant and identity (authentication) before performing operations.
     
     Risks:
     
     
       - Performance: Listing comments for an entry is efficient (Query). Getting a single comment by ID requires entryId 
   and modelId because of the PK structure. This is a trade-off for efficient listing.
       - Duplication: Had to duplicate storage logic in api-headless-cms-ddb-es because it doesn't depend on 
   api-headless-cms-ddb. This is consistent with existing architecture.
     
     The solution is modular and follows the existing Webiny architecture patterns.
